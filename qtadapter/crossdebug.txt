  ---
  How Remote Debugging Works (Plain English)

  Your WSL machine                         Raspberry Pi CM5
  ─────────────────                        ─────────────────
  Qt Creator                               Your app binary
      │                                         │
      │  starts & controls                      │  controlled by
      ▼                                         ▼
  gdb-multiarch  ←──── TCP port 2345 ────  gdbserver
  (debugger on host)                       (debug stub on Pi)

  - gdbserver is a tiny program on the Pi that runs your app and accepts
  debugger commands over the network.
  - gdb-multiarch on your WSL side sends "step", "add breakpoint", "read
  variable" commands.
  - Qt Creator is the GUI sitting in front of gdb — you click a line to set a
  breakpoint, Qt Creator tells gdb, gdb tells gdbserver.
  - The binary runs entirely on the Pi — gdb only reads symbols from the local
  copy to show you source lines.

  ---
  Workflow Every Time You Debug

  1. Build for Pi (in Qt Creator or terminal):
  make pi

  2. Copy binary to Pi:
  scp build_pi/Qt5DecoupledDemo pi@<PI_IP>:/home/pi/

  3. On the Pi, start gdbserver:
  gdbserver :2345 /home/pi/Qt5DecoupledDemo
  It prints Listening on port 2345 and waits.

  4. In Qt Creator — attach the debugger:
  Debug → Start Debugging → Attach to Running Debug Server

  ---
  What Is Actually Happening

  When GDB connects to gdbserver on the Pi, the Pi reports it is loading shared
  libraries at paths like:
  /lib/aarch64-linux-gnu/libQt5Widgets.so.5
  /lib/ld-linux-aarch64.so.1              ← the dynamic linker

  GDB prepends its sysroot to these paths to find the local copies for reading
  symbols. With the wrong sysroot it builds bad paths, finds nothing, and:

  1. Cannot set its internal breakpoint in the dynamic linker → Qt Creator 
  timeout
  2. Cannot read symbols from Qt libraries → "Could not load shared library 
  symbols"

  Your host has the aarch64 libraries in two places:

  ┌─────────────────────────────┬─────────────────────────────────────────┐
  │            Path             │                Contains                 │
  ├─────────────────────────────┼─────────────────────────────────────────┤
  │ /usr/lib/aarch64-linux-gnu/ │ Qt5, dynamic linker, all multiarch libs │
  ├─────────────────────────────┼─────────────────────────────────────────┤
  │ /usr/aarch64-linux-gnu/lib/ │ Cross-compiler sysroot (C runtime only) │
  └─────────────────────────────┴─────────────────────────────────────────┘

  Neither mirrors the Pi's path structure directly. You need a sysroot directory
  that does.

  ---
  Fix: Create a Proper GDB Sysroot

  Run these commands once in your terminal:

  sudo mkdir -p /opt/pi-sysroot/lib
  sudo mkdir -p /opt/pi-sysroot/usr

  # Pi libs live at /lib/aarch64-linux-gnu/ — map that here
  sudo ln -sf /usr/lib/aarch64-linux-gnu  /opt/pi-sysroot/lib/aarch64-linux-gnu

  # Pi dynamic linker lives at /lib/ld-linux-aarch64.so.1
  sudo ln -sf /usr/lib/aarch64-linux-gnu/ld-linux-aarch64.so.1
  /opt/pi-sysroot/lib/ld-linux-aarch64.so.1

  # Pi also has /usr/lib/aarch64-linux-gnu/ — map that too
  sudo ln -sf /usr/lib/aarch64-linux-gnu  /opt/pi-sysroot/usr/lib

  Verify it looks right:

  ls /opt/pi-sysroot/lib/
  # Should show: aarch64-linux-gnu/  ld-linux-aarch64.so.1

  ls /opt/pi-sysroot/lib/aarch64-linux-gnu/libQt5Widgets.so.5
  # Should show the file

  Now GDB with sysroot /opt/pi-sysroot will resolve paths correctly:

  Pi reports:  /lib/ld-linux-aarch64.so.1
  GDB looks:   /opt/pi-sysroot/lib/ld-linux-aarch64.so.1  ✓  ← timeout fixed

  Pi reports:  /lib/aarch64-linux-gnu/libQt5Widgets.so.5
  GDB looks:   /opt/pi-sysroot/lib/aarch64-linux-gnu/libQt5Widgets.so.5  ✓  ←
  symbols fixed

❯ do I have to copy the files from target raspberry pi ?                        

● No, you do not need to copy files from the Pi. Here is why.

  ---
  What You Already Have on Your WSL Host

  When you ran:
  sudo apt-get install libqt5*:arm64
  apt installed the ARM64 versions of Qt5 and system libraries directly on your
  WSL host via Ubuntu's multiarch support. These are real aarch64 binaries
  sitting at /usr/lib/aarch64-linux-gnu/.

  Your WSL host already has:
  /usr/lib/aarch64-linux-gnu/libQt5Widgets.so.5.15.13   ← ARM64 binary
  /usr/lib/aarch64-linux-gnu/libQt5Core.so.5.15.13      ← ARM64 binary
  /usr/lib/aarch64-linux-gnu/ld-linux-aarch64.so.1      ← ARM64 dynamic linker

  The sysroot we built with symlinks just reorganizes these into the folder 
  structure GDB expects — no new files needed.

  ---
  When Would You Need to Copy from the Pi?

  ┌─────────────────────────────────────────────────────┬───────────────────┐
  │                      Situation                      │   Need to copy?   │
  ├─────────────────────────────────────────────────────┼───────────────────┤
  │ Debugging your own app code (breakpoints,           │ No                │
  │ variables, stepping)                                │                   │
  ├─────────────────────────────────────────────────────┼───────────────────┤
  │ Pi has same Qt5 version as host multiarch packages  │ No                │
  │ (5.15.13)                                           │                   │
  ├─────────────────────────────────────────────────────┼───────────────────┤
  │ Pi has extra libraries you installed manually on    │ Yes               │
  │ the Pi                                              │                   │
  ├─────────────────────────────────────────────────────┼───────────────────┤
  │ Pi has a different Qt5 version than your host       │ Yes               │
  │ packages                                            │                   │
  ├─────────────────────────────────────────────────────┼───────────────────┤
  │ You want to step into Qt library internals (Qt      │ Yes (+ debug      │
  │ source debugging)                                   │ symbols)          │
  └─────────────────────────────────────────────────────┴───────────────────┘

  ---
  Quick Check: Are Versions Matching?

  SSH into your Pi and run:
  dpkg -l | grep libqt5widgets

  If it shows 5.15.x — the same family as your host's 5.15.13 — you are fine
  with the symlinks approach. GDB only needs the library files to match closely
  enough to resolve the dynamic linker structure. It reads your app's debug
  symbols from build_pi/Qt5DecoupledDemo, not from the Qt libraries themselves.

  ---
  The Only File GDB Truly Needs a Perfect Match For

  build_pi/Qt5DecoupledDemo    ← already on your host, exact match guaranteed

  This is your binary with full DWARF debug symbols (-g3 -O0 from the toolchain
  file). Everything else — Qt libs, libc — GDB uses only to walk the shared
  library load list and resolve the dynamic linker. An approximate version match
  is sufficient for that.
